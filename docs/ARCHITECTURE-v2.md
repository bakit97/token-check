# SOL·СКАН v2 — главный источник и пути (уточнение к ТЗ от 17.10.2026)

**Статус:** согласованные правила, реализуем постепенно. Эта спецификация имеет приоритет над противоречащими формулировками ТЗ v1.

## 1. Что такое «Все»

«Все» — **главный источник допуска монет** в систему, а не единственный набор настроек или общий список любых токенов Solana. Другие разделы получают монеты **через отдельные пути со своими фильтрами** от этого главного источника. Их фильтры не могут добавлять монеты в «Все» и не меняют его состав.

**Важно:** простая регистрация токена и появление в API не означают «выход на витрину». Начальный момент **до миграции** — когда монета стала доступна для публичной покупки на торговой площадке/кривой (по проверенному времени события). До этого она для фильтра возраста ещё не продаётся.

## 2. Два возрастных фильтра, независимо по 1–10 минут

- 🌱 **До миграции**: возраст = момент проверки минус **подтверждённый момент начала публичной торговли**. Пример: при пороге 2 минуты возраст 1:59 подходит, 2:01 — нет.
- 🎓 **После миграции**: возраст = момент проверки минус **подтверждённый момент миграции**. Если миграция произошла 30 секунд назад при пороге 2 минуты — подходит.
- Время, когда сканер впервые увидел токен, не заменяет ни один из этих моментов.
- Необоснованный, неполный или неподтверждённый момент **не является основанием для допуска**.
- Фильтр возраста применяется **при первом получении достоверного события**, а не как таймер автоматического скрытия карточки. Изменение порога не загружает задним числом пропущенные монеты.

## 3. Правило «один вход»

Для одного **mint** возможен **не более одного** успешного входа через любой поток.

| Что произошло | Что делаем |
| --- | --- |
| Подошла до миграции | Зачислить через «До». Повторного зачисления «После» нет. |
| Опоздала до миграции | Не зачислять. Если позже своевременно поймана миграция, ещё можно зачислить через «После». |
| Не попала до, но подходит после | Зачислить через «После» один раз. |
| Опоздала и до, и после | Монеты нет в «Все», нет и на дальнейших путях. |
| Уже зачислена, пришёл второй API/WS-сигнал | Не создавать дубликат. |

Непрошедшие возрастные фильтры могут фигурировать лишь во **внутренней технической диагностике источников**, но никогда как кандидаты для исследований или «Прошли».

## 4. Разветвление: отдельные фильтры путей

```text
Сетевые источники → проверка событий → возраст до/после → [«ВСЕ», принятые mint]
                                                           │
                         ┌─────────────────────────────────┼─────────────────────┐
                         │                                 │                     │
                 путь в Исследование 1             путь в Мои фильтры      другие пути
                   (свои условия)                 (активные модули)         от «Все»
                         │                                 │
                  живые/мёртвые                        «Прошли»
                         │                                 │
                  Полигон 1-го уровня              Исследование 2-го уровня
                                                           │
                                                сильные/слабые → Полигон 2
```

Данные для тестирования на обоих полигонах поступают из размеченных соответствующими исследованиями монет. **Полигон не обходит главный источник.** У каждого пути и фильтра свои настройки; отказ на одном пути не удаляет монету из «Все» и не исключает её из других разрешённых путей.

## 5. Серверное выполнение (разрабатывается)

Авторитетный вход от SourceRuntime отделён от наблюдательных кандидатов. Ветка feature/serverside-passed-r2-20261017 содержит разрабатываемые контуры. Они пока НЕ проходили завершающую проверку и НЕ опубликованы на рабочем сервере.

1. PassRuntime — первичные серверные фильтры 1-го уровня с отдельной конфигурацией. При совпадении внутри исходного окна решения запись перед показом на сайте синхронно дописывается в append-only журнал (fsync). Замораживаются момент допуска, первый сигнал, точка 0, показатели и версии правил.
2. Модули 2-го уровня НЕ могут добавить mint в «Все» или породить первичный сигнал «Прошли». Их версии сохраняются при первом совпадении, но применяются к подтверждённому второму уровню по данным до точки 0.
3. ResearchTwoRuntime берёт только серверный журнал PassRuntime, ожидает 300 минут после точки 0, проверяет полноту исторических данных цены и определяет сильные/слабые. Отсутствующие данные означают pending, а не «слабая». Размеченные строки сохраняются на диске, не более 5000 в каждом классе.
4. auto-research-v2.js готовит отдельные предварительные предложения правил каждого уровня. Обучение использует хронологически более ранние наблюдения; более поздние используются для проверки, но не для подбора того же правила. Это наблюдательная аналитика, а не торговая инструкция.
5. Настройки из localStorage не становятся серверными автоматически. Телефон может быть выключен. Сервер получает только отдельно опубликованную конфигурацию. Сайт позволяет выгрузить подготовленный pass-filters.json; прямой защищённый API остаётся задачей до запуска.
6. Новая конфигурация начинает действовать не раньше момента получения сервером новой версии. Изменение и выключение правил не переписывают исторические сигналы и не добавляют старые монеты задним числом.

### Готовящиеся источники UI

- passed-v2/status.json, passed-v2/live.json, passed-v2/day/YYYY-MM-DD.json — серверная история «Прошли».
- research-v2/status-two.json, research-v2/polygon-2.json — серверные пятчасовые результаты второго уровня.
- research-v2/auto-1.json, research-v2/auto-2.json — предварительные результаты поиска правил по отдельным двум наборам.
- research-v2/status.json, research-v2/polygon-1.json — прежняя разметка первого уровня.

Сайт должен отличать локальные черновики от авторитетного журнала. Отсутствие свежих данных не считается нулём подтверждённых сигналов.

## 6. Перед публикацией

Завершить защищённую отправку настроек с телефона, доработать управление модулями с подтверждением изменений, затем выполнить проверки восстановлений журналов, пятчасовых вычислений, пропущенных данных, отсутствия утечек будущих наблюдений, скорости на Android. Только после этого публиковать на рабочем сервере и проводить реальную проверку по монетам.

До слияния в main рабочая версия сайта и сервера остаётся прежней.
