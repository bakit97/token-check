# SOL·СКАН v2 — Управление серверными фильтрами

**Стадия:** код разрабатывается в отдельной ветке. Пока не проверен и не развёрнут в рабочем окружении.

## Безопасный путь управления

Сайт публичный (GitHub Pages), поэтому настройки из localStorage не могут становиться доверенными правилами серверного журнала. Чтение данных и изменение правил — разные права. Backend не принимает записи от анонимного браузера.

Возможны два режима:

1. Сохранить на телефоне файл pass-filters.json через вкладку «Мои фильтры», затем опубликовать файл отдельно в конфигурацию сервера через контролируемый процесс. В файле нет секретов.
2. После установки отдельной Cloud Run-службы control-api отправлять настройки из вкладки «Мои фильтры» непосредственно. Для этого нужен собственный ключ владельца, вводимый в поле типа password. Он не записывается в localStorage, файл конфигурации, логи или URL. Изменение требует отдельной галочки подтверждения.

Вторая возможность пока не активна. При отсутствии control/endpoint.json кнопка прямой публикации заблокирована, но экспорт JSON работает.

## Формат

```json
{
  "schema": 1,
  "enabled": false,
  "activatedAt": 0,
  "decisionMinutes": 10,
  "filters": [],
  "modules": []
}
```

Фильтр: id, name, level (`1` / `2`), key, op, value, version. Модуль: filterId, phase (`before` / `after`), level, enabled.

**Нулевая дата активации не означает 1970 год:** PassRuntime записывает собственное серверное время получения новой версии, сохраняет его на диске и никогда не подбирает монеты, появившиеся до включения условий. Рестарт той же версии сохраняет этот момент; повторное включение после выключения получает новую дату активации.

Первый уровень создаёт отдельную запись «Прошли» в течение исходного окна. Второй использует только запись «Прошли» и наблюдения до зафиксированной точки 0, после полной пятчасовой истории. Редактирование никогда не пересчитывает уже сохранённые записи.

## Для будущего защищённого API

- Исходник: server/control-api.js (Node.js, без зависимостей).
- Dockerfile: server/Dockerfile. Работает под непривилегированным пользователем.
- Развёртывание: workflow deploy-owner-control (запускается **только вручную**).
- Сервис должен иметь доступ к Google Cloud Storage для записи только доверенной конфигурации; рекомендуется выделенная отдельная служебная учётная запись с минимальными правами.
- SOLSCAN_CONTROL_SHA256 — 64-символьный SHA-256 *случайного отдельного ключа владельца*, задаваемый через Secret Manager. Исходный ключ не должен находиться в репозитории.
- SOLSCAN_CONTROL_ORIGIN — разрешённый origin статического сайта.
- GET/POST /api/filter-config требуют Bearer, сверяются в постоянное время; POST ограничен по размеру и числу запросов. Изменение GCS использует ifGenerationMatch, предотвращая одновременное затирание другого изменения.
- После развёртывания endpoint записывается в control/endpoint.json и становится видим сайту. Его URL публичен, но без ключа настроек не изменить.
- Рабочий сборщик перечитывает config/pass-filters.json при выгрузках; конфигурация владельца **не перезаписывается** очередной поставкой кода.

Ни один секрет нельзя помещать в GitHub Pages, общедоступный GCS JSON или в репозиторий. Выходить в работу только после проверки доступов, восстановления журналов, нормальной обработки ошибок и корректного поведения браузера.

## Независимые возрастные фильтры главного источника

- Серверная конфигурация: `config/source-age.json`, резервный файл при первом развёртывании `server/source-age.json`.
- Значения `beforeMinutes` и `afterMinutes` — независимые целые числа от **1 до 10**. Их применяет непосредственно `SourceRuntime`, а не телефон.
- `POST /api/source-age` и `GET /api/source-age` используют ту же авторизацию владельца, CORS и защиту конкурентных изменений, что `/api/filter-config`.
- В «Все» изменение подтверждается отдельной галочкой, ключ не записывается на устройство; изменение вступает в силу после загрузки главным сборщиком новой конфигурации.
- Меняется только поведение следующих проверенных событий. Допущенные монеты не исчезают, опоздавшие не возвращаются задним числом; принцип одного входа по mint остаётся неизменным.
- `server/collector.js` перечитывает конфигурацию при очередной выгрузке, обновляет persisted settings без остановки текущего журнала.

## Серверная настройка двух уровней исследования

У первого и второго уровней **разные** конфигурационные файлы и отдельные защищённые маршруты:

- `config/research-one.json` ↔ `GET/POST /api/research-one`: продолжительность 1–24 часа, доля активных пятиминутных промежутков, допустимый простой и минимальное покрытие данных.
- `config/research-two.json` ↔ `GET/POST /api/research-two`: доля 300 минут выше цены в фиксированной точке 0 и минимальное покрытие.
- Для ручной публикации без сервиса управления предусмотрен запускаемый вручную workflow `publish-owner-settings.yml`, требующий явного текста подтверждения `PUBLISH`.
- `ResearchEpoch` хранит на диске серверное время активации версии и создаёт отдельный банк размеченных наблюдений при смене порога. Старую разметку не перезаписывает, старые монеты в новую группу задним числом не добавляет. При повторном включении прежнего набора порогов начинается новая эпоха с новым банком.
- Изначальный полигон первого уровня с неизменёнными штатными порогами может продолжить старый банк `research-v2-bank.json`, чтобы не терять накопленные наблюдения.
- Если не хватает полных пятчасовых наблюдений или подтверждённых событий, результат остаётся «ожидание», не подменяется ошибочным «слабый»/«мёртвый».

Изменение из телефона требует ключа владельца, отдельной галочки подтверждения и действующего Cloud Run API. Ключ не сохраняется в файлах клиента. Сам факт принятия конфигурации API не означает, что collector уже применил её: экран отображает новое значение только после прихода серверного статуса.

## Разделение серверных файлов

- source/... — авторитетный главный журнал входа mint.
- passed-v2/... — серверный журнал совпадений и версии условий.
- research-v2/polygon-1.json — живая/мёртвая разметка по торговой активности.
- research-v2/polygon-2.json — сильная/слабая разметка только по прошедшим первичный путь.
- research-v2/auto-1.json и auto-2.json — предварительные предложения из хронологически разделённых групп.

Нет исполнения покупок или продаж: все процессы работают только с наблюдениями и исследовательской классификацией.

## Проверки перед слиянием в main

Пока отложены по запросу: unit/integration, рестарт с подрезанным журналом, смена конфигурации в полёте, отсутствие задним числом зачислений, пять часов и пробелы цены, no-leakage данных, права GCP, мобильные устройства и реальная сеть. Новая ветка не должна запускать изменения рабочего сервера до прохождения этого этапа.
